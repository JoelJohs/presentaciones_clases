# Fundamentos de Redes y Tráfico en Internet

Analiza el modelo cliente-servidor, direccionamiento IP público y privado, resolución de nombres (DNS), enrutadores y comandos de diagnóstico de red (ping, traceroute).

## 1. Roles en la Red: Petición y Respuesta <Icon name="lucide:arrow-left-right" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Cada intercambio de datos en Internet ocurre entre dos participantes con funciones distintas:

- **El cliente:** Inicia la conexión y solicita recursos específicos, como un archivo HTML, una imagen o un video.
- **El servidor:** Mantiene un proceso en espera de solicitudes entrantes, procesa cada petición y devuelve los datos correspondientes.

> **Definición técnica (Kurose & Ross, Computer Networking, §2.1.1):**
> "En una arquitectura cliente-servidor, un host siempre activo (el servidor) atiende las solicitudes de múltiples hosts clientes. Los clientes no se comunican entre sí."

Tu navegador o aplicación móvil no intercambia datos directo con otros teléfonos para obtener contenido web. Toda solicitud viaja a un servidor que procesa y entrega la información.

## 4. Localización del Servidor: Dirección IP y Puertos <Icon name="lucide:network" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Para enviar una solicitud al destino correcto, el cliente utiliza dos parámetros del protocolo de red:

* **Dirección IP:** Número identificador del equipo en la red (ejemplo: `142.250.80.46`). Sin esta dirección, los enrutadores no pueden canalizar los paquetes.
* **Número de puerto:** Identificador del proceso o servicio específico dentro del sistema operativo del servidor.
  * **Puerto 80:** Protocolo HTTP (tráfico web sin cifrar).
  * **Puerto 443:** Protocolo HTTPS (tráfico web cifrado con TLS).
  * **Puerto 22:** Protocolo SSH (administración remota segura).
  * **Puerto 53:** Servicio DNS (traducción de nombres a direcciones IP).

> **Concepto de socket (Kurose & Ross, §2.1.2):**
> Un socket actúa como el punto final de comunicación entre dos procesos. La aplicación escribe datos en el socket local y el sistema operativo los entrega al socket del equipo receptor a través de la red.

## 6. Actividad Práctica: Inspección de Red en el Navegador <Icon name="lucide:terminal" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Comprueba el flujo cliente-servidor capturando peticiones HTTP reales desde tu propio equipo:

1. **Abre las herramientas de desarrollo:** En tu navegador, presiona `F12` o la combinación `Ctrl + Shift + I`.
2. **Selecciona la pestaña Red (Network):** Verifica que el botón de grabación esté activo (círculo rojo o barra encendida).
3. **Carga una página web:** En la barra de navegación escribe `example.com` y presiona `Enter`.
4. **Inspecciona la primera petición:**
   - Haz clic sobre el primer elemento de la lista (el recurso `example.com`).
   - Abre la pestaña **Encabezados (Headers)**.
5. **Verifica los siguientes campos:**
   - **Request URL:** Dirección completa del recurso solicitado.
   - **Request Method:** Método HTTP (`GET`).
   - **Status Code:** Código de respuesta devuelto por el servidor (`200 OK`).
   - **Remote Address:** Dirección IP del servidor y puerto utilizado (ejemplo: `93.184.215.14:443`).
6. **Comprueba el resultado:** Identifica qué equipo funcionó como cliente y cuál como servidor durante la carga.

## 7. Identificadores en Internet: IP Pública y Privada <Icon name="lucide:globe-2" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Cada equipo conectado a una red informática requiere un identificador numérico para transmitir y recibir paquetes: la **dirección IP** (*Internet Protocol*).

El protocolo IPv4 divide la comunicación en dos ámbitos de red:

- **Ámbito privado (LAN):** Identifica a cada dispositivo dentro de la red de área local en tu casa, escuela o laboratorio. Los equipos externos en Internet no acceden a estas direcciones sin un enrutador intermediario.
- **Ámbito público (WAN):** Identifica a la red local completa frente al resto de Internet. Los servidores externos dirigen sus respuestas a esta dirección.

## 9. Traducción de Direcciones de Red (NAT) <Icon name="lucide:split" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Cuando un dispositivo con IP privada solicita datos a un servidor externo, el enrutador ejecuta el proceso **NAT (*Network Address Translation*)**:

1. **Salida del paquete:** Tu computadora (`192.168.1.15:52431`) envía una solicitud web. El router reemplaza la IP privada de origen por su IP pública (`201.140.85.12:61001`).
2. **Registro en tabla NAT:** El router anota en memoria que la respuesta al puerto `61001` corresponde a la IP interna `192.168.1.15`.
3. **Respuesta del servidor:** El servidor remoto responde enviando los datos a la IP pública del router.
4. **Reenvío interno:** El router consulta la tabla NAT, traduce la dirección de destino y entrega los paquetes a tu computadora.

## 10. Actividad Práctica: Descubre tus Direcciones IP <Icon name="lucide:laptop" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Comprueba la diferencia entre tu identidad local y tu identidad pública:

1. **Obtén tu IP privada:**
   - En Windows: Abre la consola (`cmd`), escribe `ipconfig` y presiona `Enter`.
   - En Linux o macOS: Abre la terminal, escribe `ip a` o `ifconfig` y presiona `Enter`.
   - Localiza la línea **Dirección IPv4**. Comprueba que pertenezca al rango de red privada (`192.168.x.x` o `10.x.x.x`).
   - Identifica la **Puerta de enlace predeterminada** (*Default Gateway*): es la IP privada del router local (como `192.168.1.1` o `192.168.0.1`).
2. **Obtén tu IP pública:**
   - En la terminal ejecuta: `curl ifconfig.me`.
   - Compara el resultado con tu IP privada. La dirección pública pertenece a un bloque asignado por tu proveedor de Internet.
3. **Compara con otro dispositivo:**
   - Conecta dos equipos a la misma red Wi-Fi o del aula y consulta la IP pública en ambos.
   - Comprueba que ambos equipos comparten la misma dirección pública, pero tienen direcciones privadas distintas.

## 11. DNS: El Directorio de Nombres de Internet <Icon name="lucide:book-open" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Las personas recuerdan nombres como `youtube.com` o `wikipedia.org`. Los enrutadores de red procesan direcciones IP numéricas como `142.250.190.46`.

El **Sistema de Nombres de Dominio (DNS)** es la base de datos distribuida que traduce nombres de host a direcciones IP numéricas.

### ¿Por qué no existe una base de datos centralizada?

Centralizar todos los nombres de Internet en un único servidor provocaría cuatro fallos críticos de diseño (Kurose & Ross, §2.4.1):

1. **Punto único de fallo:** Si el servidor central colapsa, la navegación en Internet se detiene.
2. **Volumen de tráfico:** Miles de millones de dispositivos enviando peticiones por segundo saturan cualquier nodo central.
3. **Distancia física:** La latencia entre continentes degrada el tiempo de respuesta por retardo de propagación.
4. **Mantenimiento inmanejable:** Actualizar millones de registros nuevos por minuto en un solo repositorio causa inconsistencias de datos.

La arquitectura de Internet resuelve esto mediante una **base de datos jerárquica y distribuida**.

## 13. Consultas Iterativas, Recursivas y Memoria Caché <Icon name="lucide:refresh-cw" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

El proceso de resolución combina dos tipos de peticiones entre los hosts:

* **Consulta recursiva:** Tu computadora delega la carga completa en el DNS local: *"Encuentra la IP de este dominio y devuelve el resultado final"*.
* **Consulta iterativa:** El DNS local consulta en orden al servidor Raíz, al servidor TLD y al servidor Autoritativo hasta obtener la respuesta definitiva.

### El rol de la memoria caché y el TTL (Time-To-Live)

Para evitar consultar la jerarquía global en cada clic, los servidores DNS locales guardan copias de las respuestas recientes en su memoria caché:

* **TTL (Tiempo de vida):** Cada registro DNS viaja con un temporizador en segundos asignado por el servidor autoritativo.
* Mientras el TTL no expire, el DNS local responde desde su memoria caché en menos de 5 milisegundos sin consultar servidores externos.
* Cuando el temporizador llega a cero, el DNS local purga el registro y vuelve a consultar la jerarquía global en la siguiente petición.

> **Distribución de carga geográfica:** Los servidores autoritativos de grandes plataformas asocian un mismo nombre de dominio a múltiples direcciones IP. Cada consulta devuelve la lista en orden rotatorio o la IP del centro de datos más cercano al usuario.

## 15. Seguridad en DNS: Envenenamiento de Caché y Mitigación <Icon name="lucide:shield-alert" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

El protocolo DNS carece de autenticación nativa en su diseño base, lo que expone la red a vectores de ataque:

* **Envenenamiento de caché (DNS Cache Poisoning):** Un atacante envía respuestas falsificadas a un servidor DNS local mientras este espera contestación de un servidor autoritativo. Si el resolver acepta los paquetes falsos, almacena una IP maliciosa en caché. Los usuarios locales que busquen `bancoreal.com` terminan en el servidor del atacante hasta que expire el TTL.
* **Ataques de denegación de servicio (DDoS):** Intentos de saturar servidores Raíz mediante botnets masivas. La red resiste gracias a réplicas Anycast globales y al filtrado de tráfico absorbido por las cachés de los proveedores locales.
* **Mitigación con DNSSEC:** Las extensiones de seguridad para DNS (*DNS Security Extensions*) firman las respuestas con pares de claves pública y privada para verificar el origen y bloquear datos alterados.

## 16. Actividad Práctica: Inspección de Registros DNS con nslookup <Icon name="lucide:terminal" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Usa la herramienta nativa `nslookup` en tu terminal para auditar la infraestructura DNS de un dominio:

1. **Abre tu terminal:** En Windows usa PowerShell o `cmd`. En Linux o macOS usa Terminal.
2. **Inspecciona direcciones IPv4 (Tipo A):**
   ```bash
   nslookup mercadolibre.com
   ```
   Observa si la respuesta lista múltiples direcciones IP. Esto comprueba que el dominio aplica balanceo de carga entre varios servidores.
3. **Consulta los servidores de correo electrónico (Tipo MX):**
   ```bash
   nslookup -type=MX mercadolibre.com
   ```
   Identifica qué plataforma gestiona la recepción de correos de la organización.
4. **Consulta los servidores autoritativos (Tipo NS):**
   ```bash
   nslookup -type=NS mercadolibre.com
   ```
   Identifica los nombres de los servidores responsables de publicar las respuestas oficiales de esa zona.
5. **Inspecciona la caché DNS de tu sistema operativo (Windows):**
   ```bash
   ipconfig /displaydns
   ```
   Revisa las entradas almacenadas en tu memoria RAM local junto con su tiempo restante de expiración (TTL).

## 17. Enrutadores: Conmutación de Paquetes en la Red <Icon name="lucide:route" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Un enrutador (*router*) es un dispositivo de red que conecta múltiples enlaces de transmisión y reenvía paquetes entre redes distintas.

Internet opera como una malla de redes interconectadas donde los enrutadores funcionan como nodos de enlace.

Sus dos funciones operativas son:
* **Inspección de cabeceras:** Leer la dirección IP de destino encapsulada en cada paquete entrante.
* **Selección de ruta:** Determinar por cuál enlace físico emitir el paquete para aproximarlo a su destino.

---

## 18. Navegación Salto a Salto y Tablas de Reenvío <Icon name="lucide:milestone" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Cada enrutador conoce el siguiente nodo de paso (*next-hop*), sin almacenar la ruta completa de la red en los paquetes.

> **Analogía de la ruta (Kurose & Ross, §1.3):**
> Un conductor viaja entre ciudades lejanas sin mapa de carreteras. En cada cruce principal se detiene a preguntar cuál autopista tomar. El encargado del cruce indica el tramo inmediato y le indica consultar de nuevo en el siguiente cruce. La red opera igual: salto a salto (*hop by hop*).

### Coincidencia de prefijo más largo (Longest Prefix Match)

Cada enrutador mantiene en memoria una **Tabla de Reenvío** (*Forwarding Table*). Cuando llega un paquete:

1. El enrutador extrae la dirección IP de destino de la cabecera.
2. Compara la IP con los rangos de red registrados en su tabla.
3. Si la IP coincide con más de una entrada, aplica la regla de **coincidencia de prefijo más largo**: selecciona la ruta con la máscara de red más específica (mayor cantidad de bits coincidentes).
4. Envía el paquete por la interfaz física asociada a esa entrada.

---

## 19. Almacenamiento y Reenvío (Store-and-Forward) <Icon name="lucide:archive" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Un enrutador opera bajo el principio de **Almacenamiento y Reenvío** (*Store-and-Forward*):

1. **Recepción completa:** El conmutador recibe todos los bits del paquete en su memoria intermedia (*búfer*) antes de transmitir el primer bit al enlace de salida.
2. **Validación:** Comprueba la integridad de la cabecera del paquete mediante sumas de verificación (*checksum*). Si detecta errores de bits, descarta el paquete dañado.
3. **Cola de espera:** Si el enlace de salida transmite otros datos, el paquete aguarda su turno en la cola de salida (*output buffer*).

> **Retardo de transmisión:** Si un paquete contiene $L$ bits y el enlace transmite a una tasa de $R$ bits por segundo, el tiempo necesario para emitir el paquete completo es $L/R$ segundos por cada salto.

## 22. Diagnóstico de Conectividad con ping e ICMP <Icon name="lucide:activity" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

La herramienta `ping` verifica la disponibilidad de un host remoto y mide el retardo de ida y vuelta de los paquetes.

Opera mediante el protocolo **ICMP** (*Internet Control Message Protocol*):
1. El emisor envía un mensaje **ICMP Echo Request** (tipo 8) a la dirección IP de destino.
2. Si el host remoto está activo y no bloquea el tráfico de control, devuelve un mensaje **ICMP Echo Reply** (tipo 0).

```bash
ping google.com
```

### Parámetros de salida de ping

* **Tiempo de ida y vuelta (RTT - Round-Trip Time):** Tiempo en milisegundos (`time=18ms`) que tarda el paquete en viajar al destino y regresar. Es la suma del retardo de transmisión, propagación física por cables, procesamiento en routers y colas de espera.
* **Pérdida de paquetes (Packet Loss):** Porcentaje de paquetes descartados en la ruta por congestión en enrutadores o enlaces inestables.
* **TTL (Time-To-Live):** Contador de saltos restantes. Cada enrutador intermedio resta 1 a este valor antes de reenviar el paquete.

> Si la consola muestra `Request timed out` o `Destination host unreachable`, el host está apagado, la ruta carece de enlace hacia esa red o un cortafuegos (*firewall*) descarta el tráfico ICMP por política de seguridad.

---

## 23. Trazado de Rutas con traceroute y tracert <Icon name="lucide:map-pin" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

El comando `ping` solo comprueba la respuesta del destino final. En contraste, `traceroute` (en Linux/macOS) y `tracert` (en Windows) reconstruyen la secuencia completa de enrutadores intermedios.

```bash
# En Windows
tracert google.com

# En Linux o macOS
traceroute google.com
```

### Mecanismo de rastreo mediante TTL (Kurose & Ross, §1.4.3)

El comando utiliza una técnica basada en el campo TTL del protocolo IP y mensajes ICMP:

1. Envía paquetes con **`TTL = 1`**. El primer enrutador de la ruta decrementa el TTL a 0, descarta el paquete y devuelve un mensaje **ICMP Time Exceeded** al emisor. El comando anota la IP y el tiempo de respuesta del primer salto.
2. Envía paquetes con **`TTL = 2`**. El segundo enrutador descarta el paquete y devuelve otro mensaje de tiempo excedido.
3. El proceso se repite incrementando el TTL de uno en uno hasta alcanzar el host de destino.

> Las líneas con asteriscos (`* * *`) indican enrutadores configurados para descartar sondas ICMP o UDP sin responder, protegiendo su topología interna contra escaneo de red.

## 25. Actividad Práctica: Auditoría de Conexión en el Aula <Icon name="lucide:wrench" class="inline w-6 h-6 align-text-bottom text-brand-primary" />

Ejecuta una auditoría técnica paso a paso para diagnosticar la red de tu equipo:

1. **Identifica tu interfaz local:**
   Abre la terminal y ejecuta `ipconfig` (Windows) o `ip a` (Linux/macOS). Anota tu dirección IPv4 privada y la dirección de la **Puerta de enlace predeterminada** (*Default Gateway*).
2. **Evalúa tu enlace local (primer salto):**
   Ejecuta un ping hacia tu puerta de enlace:
   ```bash
   ping 192.168.1.1
   ```
   *(Sustituye por la IP real de tu gateway).* Comprueba que el tiempo de respuesta sea inferior a 5 ms. Esto confirma que tu cable ethernet o antena Wi-Fi opera sin congestión local.
3. **Compara latencia local frente a transoceánica (RTT):**
   - Ejecuta un ping a un servidor regional cercano:
     ```bash
     ping google.com
     ```
   - Ejecuta un ping a un servidor ubicado en otro continente:
     ```bash
     ping u-tokyo.ac.jp
     ```
   - Registra el RTT mínimo y máximo de ambos destinos. Observa el incremento de milisegundos provocado por la distancia física y el tránsito por cables submarinos de fibra óptica.
4. **Mapea los enrutadores de la ruta:**
   Ejecuta el trazado de ruta hacia un dominio público:
   ```bash
   tracert google.com
   ```
   *(En Linux usa `traceroute google.com`).* Identifica en qué número de salto sales de la red local del aula y cuántos enrutadores intermedios intervienen hasta alcanzar el destino.
